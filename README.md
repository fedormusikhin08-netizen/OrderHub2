# OrderHub — учёт заказов интернет-магазина

Итоговый проект по контрольным точкам **КТ31–КТ39** («Коллекции, LINQ, перечислители и итераторы в C#»).

Консольное приложение, которое последовательно обрастает возможностями:
очередь и стек заказов, история на `LinkedList`, склад на `Dictionary`,
сортировка каталога, отчёты на LINQ, ленивые итераторы и собственная
коллекция `CircularBuffer<T>` с поддержкой `foreach`.

## Как собрать и запустить

```bash
dotnet build OrderHub.sln
dotnet run --project src/OrderHub
```

Требования: .NET SDK 8.0 или новее.

## Вопросы к защите

1. Разница в порядке доступа. Queue<T> — FIFO: Enqueue кладёт в конец, Dequeue забирает из начала. Stack<T> — LIFO: Push и Pop работают с вершиной. В проекте очередь нужна для pendingQueue, потому что заказы обрабатываются в порядке поступления, а стек — для undoHistory, где первым отменяется последнее действие. Основные операции у обеих O(1), так что выбираешь по смыслу задачи, а не по скорости.

2. AddLast возвращает узел, который только что вставили (LinkedListNode<T>). Держать его в current выгодно: следующая вставка AddAfter(current, order) не требует поиска и работает за O(1). Find пришлось бы гонять по цепочке (O(n)), да и сравнивает он значения, а для Order это ссылка, так что найти «такой же» заказ по данным не получится. В InitHistory я как раз так и делаю: current = orderHistory.AddLast(order).

3. Индексатор должен вернуть значение типа TValue, а для отсутствующего ключа возвращать нечего, поэтому Dictionary бросает KeyNotFoundException. Это не баг, а защита от молчаливого default. Избежать просто: TryGetValue(key, out value) — один проход по хешу, bool-результат и значение. Альтернативы — ContainsKey с последующим индексатором (два поиска) или GetValueOrDefault. В WarehouseService везде TryGetValue, поэтому «товара нет» — это false и сообщение в консоль.

4. IComparable<T> реализует сам класс и задаёт естественный порядок (у Product — по цене), его подхватывает Sort() без параметров. IComparer<T> — внешний объект-сравнитель для альтернативного порядка, он передаётся в Sort(new NameComparer()) или Sort(new PriceDescComparer()), сам Product при этом не меняется. Если не реализовано ни то, ни другое, Sort() выбросит InvalidOperationException (внутри ArgumentException от Comparer<T>.Default): сравнивать нечем. На пустом списке или из одного элемента ошибки не будет, потому что сравнение не понадобится.

5. Отложенное выполнение значит, что LINQ-метод возвращает не результат, а объект-запрос. Пока его не перебрали, ни Where, ни OrderBy не выполняются. Обход начинается в момент потребления: foreach, ToList, Count, First, Sum и так далее. Важное следствие — запрос выполняется заново при каждом переборе, а не кешируется. В ReportService цепочки заканчиваются ToList, поэтому там результат уже материализован, а OrderStream.Orders() вообще ничего не делает до первого MoveNext.

6. IGrouping<TKey,TElement> — это не просто набор элементов, а набор с ключом: свойство Key плюс реализация IEnumerable<TElement>. GroupBy возвращает последовательность таких групп, и внутри каждой работают обычные LINQ-операции: Count(), Sum(), Average(), Where, Select. Именно поэтому в SummarizeByCategory агрегаты считаются на группе, без ручного цикла. От словаря IGrouping отличается тем, что это последовательность, а не хеш-таблица, и порядок групп идёт по первому появлению ключа.

7. Join работает как соединение по ключу: для второй последовательности строится хеш-таблица, затем первая перебирается и для каждого ключа достаются совпадения. Это inner join, пары без совпадения отбрасываются. Если у клиента несколько заказов, он даст несколько строк результата, по строке на заказ. Поэтому дальше GroupBy по имени и Sum: несколько строк схлопываются в одну сумму. Если бы клиентов соединяли по Id, было бы то же самое, просто ключ был бы числовой.

8. Секрет в том, что метод с yield return при вызове не исполняется. Компилятор превращает его в класс-перечислитель, и тело крутится по шагу на каждый MoveNext. while(true) в Orders() не страшен: за один шаг отдаётся один заказ, а продолжение цикла происходит только по запросу. Take(N) запрашивает ровно N элементов, после чего перестаёт дёргать MoveNext и вызывает Dispose, итератор останавливается. А если написать Orders().ToList(), программа действительно повиснет.

9. IEnumerable<T> требует реализации и обычного IEnumerable, он у него в предках. У обычного GetEnumerator возвращаемый тип IEnumerator, у обобщённого — IEnumerator<T>, это разные сигнатуры. Поэтому класс с одним GetEnumerator() не закроет оба интерфейса: нужна явная реализация IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();. Она же не даёт лишнему методу торчать в публичном API. В CircularBuffer без неё код просто не скомпилируется.

10. У кольцевого буфера next — индекс, куда ляжет следующий элемент, а size — сколько элементов реально хранится. Тогда индекс самого старого: (next - size + capacity) % capacity. Прибавка capacity спасает от отрицательного числа перед %. Дальше обход идёт по кругу: index = (index + 1) % capacity. В обратную сторону — с (next - 1 + capacity) % capacity и шагом (index - 1 + capacity) % capacity.

11. В девяти отдельных заданиях каждый раз начинаешь с нуля и не видишь, как темы связаны. Здесь один домен (заказы, товары, клиенты) и один код, который постепенно растёт: очередь и стек живут рядом с историей на LinkedList, отчёты читают те же данные, итераторы порождают те же заказы, а CircularBuffer показывает, как устроен foreach изнутри.
