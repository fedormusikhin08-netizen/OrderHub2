## 2. Цель и задачи проекта

**Цель:** за один сквозной проект последовательно освоить девять тем раздела «Коллекции, LINQ, перечислители и итераторы» — от `List<T>`, `Stack<T>` и `Queue<T>` до пользовательских типов, поддерживающих `foreach`, — и закрепить навык поэтапной разработки: каждый этап пишется, проверяется, фиксируется в Git и отправляется в GitHub отдельным коммитом в своей ветке.

**Сюжет:** консольное приложение **OrderHub** — «Учёт заказов интернет-магазина». Оно последовательно обрастает возможностями:

1. очередь необработанных заказов, стек отмены, полный список (КТ31);
2. история заказов клиента со вставкой после текущего узла (КТ32);
3. склад товаров: поступление, продажа, безопасный поиск (КТ33);
4. три способа сортировки каталога (КТ34);
5. отчёт «дорогие товары» цепочкой `Where → OrderBy → Select` (КТ35);
6. сводка по категориям через `GroupBy` (КТ36);
7. соединение заказов и клиентов через `Join`, топ-3 клиентов через `Take` (КТ37);
8. ленивый генератор заказов на `yield return` (КТ38);
9. собственная коллекция `CircularBuffer<T>` с `foreach` и обратным обходом (КТ39).

Приложение запускается в консоли, автоматически печатает все отчёты (пункт «0» меню) и имеет интерактивное меню из 12 пунктов для защиты.

### Этап 9. КТ39 — собственный `IEnumerable<T>` (коммит `66c1701`, ветка `stage/39-custom-iterator`)

**Задача:** класс `CircularBuffer<T>` с `foreach` и обратным обходом.

**Реализация:** внутренний массив `T[] buffer`, счётчики `next`, `size`, `capacity`; конструктор отбрасывает `capacity <= 0` (`ArgumentOutOfRangeException`). `Add` пишет элемент и сдвигает `next = (next + 1) % capacity`, увеличивая `size` только пока буфер не заполнен (старый элемент перезаписывается). Оба обхода написаны через `yield return` (собирать `List<T>` и возвращать её нельзя):

```csharp
public IEnumerator<T> GetEnumerator()
{
    int index = (next - size + capacity) % capacity;   // индекс самого старого
    for (int i = 0; i < size; i++)
    {
        yield return buffer[index];
        index = (index + 1) % capacity;
    }
}
```

`Reverse()` идёт назад: `index = (index - 1 + capacity) % capacity`. Неуниверсальный метод реализован явно: `IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();`.

**Вывод консоли (ёмкость 3, добавлены «1»…«5»):**

```
Обход foreach (от старого к новому): 3, 4, 5
Обход Reverse() (от нового к старому): 5, 4, 3
Count = 3, IsFull = True
Через LINQ Select: [3] [4] [5]
```

## 5. Пояснения ключевых решений

**Чем `List` отличается от `LinkedList`.** `List<T>` — непрерывный массив: быстрый доступ по индексу `O(1)`, но вставка в середину требует сдвига элементов `O(n)` и может приводить к перевыделению памяти. `LinkedList<T>` — цепочка узлов со ссылками `Previous/Next`: доступ по индексу невозможен (`O(n)` поиск), но вставка рядом с уже найденным узлом — `O(1)` без сдвига. Поэтому весь список заказов хранится в `List` (нам нужен порядок добавления и индексный доступ), а история клиента, куда мы вставляем заказ относительно текущего узла, — в `LinkedList`.

**Почему чтение словаря через `TryGetValue`.** Индексатор `d[key]` для отсутствующего ключа бросает `KeyNotFoundException`, и обработчик исключений — дорогой и неочевидный способ проверки наличия. `TryGetValue(key, out value)` за один вызов проверяет наличие и возвращает значение, а его `bool`-результат заставляет программиста явно обработать оба исхода. Удаление — через `Remove` с проверкой результата, поэтому `KeyNotFoundException` в проекте не возникает ни разу.

**Чем отличаются `IComparable` и `IComparer`.** `IComparable<T>` задаёт один «естественный» порядок внутри самого типа — его использует `List.Sort()` без аргументов, порядок зашит в класс `Product`. `IComparer<T>` — отдельный класс для альтернативного порядка: тип не меняется, порядок подбирается под задачу (`NameComparer`, `PriceDescComparer`). Третий способ — разовый порядок лямбдой, соответствующей делегату `Comparison<T>`: он живёт только в месте вызова.

**Что такое отложенное (ленивое) выполнение.** LINQ-запрос — это не данные, а описание запроса. Реальный обход происходит только при «потреблении» результата: в `ToList`, `Count`, `foreach`, `First`. Пока результат не использован, код тела запроса не выполняется ни разу. То же свойство у итераторов `yield return`: тело метода исполняется ровно до очередного `yield` и только когда потребитель вызвал `MoveNext`. Поэтому `Orders()` при вызове не печатает ничего, а `Orders().ToList()` завис бы — бесконечному итератору всегда есть что отдать; `Take(N)` ограничивает обход.

**Чем `IGrouping<TKey,TElement>` отличается от обычной коллекции.** Это представление группы: `Key` — значение ключа, а сам объект реализует `IEnumerable<TElement>` и поддерживает любые LINQ-операторы (`Count()`, `Sum()`, `Average()`, ещё один `Select` и т.д.), что позволяет считать агрегаты прямо на группе, не выходя из цепочки.

**Как работает `Join`.** Внутри — хеш-таблица: по ключу второй коллекции строится индекс, затем каждая запись первой коллекции соединяется со всеми совпавшими. Если у одного клиента несколько заказов — на каждую пару приходится своя строка результата, поэтому после `GroupBy` по имени клиента получаем корректные суммы.

**Зачем явная реализация `IEnumerable.GetEnumerator`.** `IEnumerable<T>` наследует нетипизированный `IEnumerable` и требует метод с сигнатурой `GetEnumerator()`, возвращающей `IEnumerator`. Типизированная версия возвращает `IEnumerator<T>` — это другой тип, и без явной реализации `IEnumerator IEnumerable.GetEnumerator()` класс не проходит контракт интерфейса; `foreach` по нетипизированному объявленному коллекции перестал бы работать.

**Индекс самого старого элемента кольцевого буфера.** `next` указывает на позицию следующей записи, `size` — сколько элементов реально хранится (после заполнения `size == capacity`). Самый старый лежит на `(next - size + capacity) % capacity` (прибавление `capacity` нужно, чтобы индекс не стал отрицательным по модулю).

**Почему один проект с девятью этапами лучше девяти отдельных заданий.** Каждый этап опирается на предыдущий: склад использует те же заказы, отчёты — те же товары и клиентов, итераторы порождают объекты того же домена. Студент видит эволюцию кода, учится поэтапно интегрировать изменения, вести Git-историю и защищать цельную систему, а не девять несвязанных фрагментов.
